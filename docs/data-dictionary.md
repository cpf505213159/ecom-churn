# 数据字典与口径说明

> 这份文件描述的是**公司宽表的字段结构**（可带走的部分），数据本身不外带。
> 仓库里的 `outputs/user_snapshot.csv` 是按同一结构生成的同构数据，用于验证方法。

---

## 一、用户快照表（建模输入）

一人一行，快照时点 = 观察窗终点（2024-09-15）。

| 字段 | 类型 | 口径 | 是否入模 |
|---|---|---|---|
| `user_id` | bigint | 用户 ID | 否（主键） |
| `tenure_days` | int | 注册至快照时点的天数 | ✅ |
| `recency_days` | int | 距最近一次下单的天数；从未下单记 999 | ✅ |
| `freq_30d` | int | 观察窗内订单数 | ✅ |
| `orders_90d` | int | 近 90 天订单数 | ✅ |
| `gmv_90d` | decimal | 近 90 天支付金额（已剔除退款与测试单） | ✅ |
| `browse_30d` | int | 观察窗内浏览 PV | ✅ |
| `search_30d` | int | 搜索次数 | ✅ |
| `cart_30d` | int | 加购次数 | ✅ |
| `tickets_30d` | int | 客服工单数（剔除物流延迟类） | ✅ |
| `return_rate_90d` | decimal | 退款单 / 总单 | ✅ |
| `cat_diversity` | int | 购买过的叶子类目数 | ✅ |
| `is_new` | 0/1 | `tenure_days < 90` | ✅ |
| `coupon_received_30d` | 0/1 | 是否收到券 | ❌ **干预结果** |
| `coupon_used_30d` | 0/1 | 是否使用券 | ❌ **干预结果，且与「被留住」互为因果** |
| `churn` | 0/1 | 标签窗内是否下单（0 = 流失） | 标签 |

## 二、标签口径

| 项 | 设定 | 理由 |
|---|---|---|
| 观察窗 | 2024-08-01 ~ 2024-09-14（45 天） | 覆盖至少两个完整购买周期 |
| 标签窗 | 2024-09-15 ~ 2024-10-14（30 天） | 足够观察一次复购 |
| 用户池 | 观察窗内有活跃（浏览或下单） | 排除长期沉默账户，避免虚增正样本 |
| 正样本 | 标签窗内无支付订单 | 退款单不计入「有下单」 |
| 分群 | 新客（注册 < 90 天）/ 老客 | 新客流失定义不同，混在一起评估会失真 |

## 三、为什么是 45 天

平台整体购买周期中位数 **21 天**。
若按「30 天无购买 = 流失」，会把这个周期右侧的正常低频用户全部错标为正样本——
第一版正样本率 31%，改到 45 天后降到 13%，与运营的直觉一致（他们说「一个月不来的，大概三成是真走了」）。

**代价**：标签要等 30 天才能拿到，模型最早只能在 10 月中旬训练，
所以上线节奏是「月度打分」，做不到实时。

## 四、为什么砍掉券特征

训练集里加 `coupon_used_30d`，AUC 从 **0.766 虚高到 0.796**（本仓库可复现）。
但这个特征是运营干预的产物：

- 训练时可见：因为券已经发出去、已经用了；
- 上线时不可知：你不可能知道「这个人明天会不会用券」；
- 方向还反了：用过券的人本来就被留住了一部分，模型学到的「用券 = 不流失」，
  在真实投放里会变成「只给已经用券的人发券」——典型的自我实现。

所以它在特征白名单之外，`src/model.py` 里用 `LEAKY` 单独列出，做对照实验用。

## 五、指标口径

| 指标 | 定义 | 备注 |
|---|---|---|
| AUC | 随机取一个流失用户与一个留存用户，模型给前者打分更高的概率 | 时间外验证，不是随机切分 |
| KS | 正负样本累计分布的最大间距 | 通常 AUC 0.78 对应 KS 0.40 左右 |
| 召回 | 名单内真实流失用户 / 全部真实流失用户 | 分母是标签窗的真实流失人数 |
| 精确率 | 名单内真实流失比例 | 决定「券发给多少人会浪费」 |
| lift | 名单内流失率 / 大盘流失率 | 比 AUC 更能让运营听懂 |
| 触达成本 | 触达人数 × 单次成本（短信 0.04 + 券 0.31 ≈ 0.35 元） | 券成本按实际核销率折算 |
