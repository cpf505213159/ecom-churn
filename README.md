# 电商用户流失预警 · 口径与方法包

一个「可以带走」的流失项目：**数据是公司的，不能带；口径、特征、阈值逻辑、成本核算、评估方法是分析师的，可以带。**

这个仓库把那部分资产整理成可运行的最小件——一份带输出的 Notebook、三份生产可用的 SQL、一份数据字典，
并且在同构数据上验证了每条方法判断是否成立。

```bash
pip install -r requirements.txt
python scripts/run_notebooks.py     # 跑出 Notebook 的全部输出
pytest tests -q                     # 5 个测试，覆盖 AUC/KS/阈值/泄漏
```

---

## 一、这个项目回答什么

平台月活下滑，运营的应对是「每月对全量用户发券」。预算固定，全量发等于每人只够几毛钱；
而且没人说得清「谁会流失」——只能凭感觉挑人群。

目标不是把 AUC 做高，而是给出**一份运营能承接、能解释、能算清成本的名单**。

| 约束 | 具体值 | 对方案的影响 |
|---|---|---|
| 触达能力 | 每月最多 80 万人（全量 1200 万的可触达用户） | 阈值必须按承接量倒推，不能按 F1 |
| 信息可得性 | 只能用「下单前」就能拿到的信息 | 券类特征全部排除 |
| 可解释性 | 运营要知道「为什么这个人高危」 | 逻辑回归 + 分档 lift，不上黑箱 |
| 时效 | 标签要等 30 天 | 只能月度打分，做不到实时 |

## 二、三个关键判断（都有可运行证据）

**1. 标签用 45 天观察窗，不用 30 天**
平台购买周期中位数 21 天，30 天窗口会把正常低频用户错标成流失（正样本率 31% → 改 45 天后 13%）。
口径写在 `sql/01_label.sql` 的注释里，避免下次返工。

**2. 券特征必须砍掉**
加上 `coupon_used_30d` 后 AUC 从 **0.774 虚高到 0.810**——但这是泄漏：
券是运营干预的产物，训练时可见、上线时不可知，而且方向是「用过券 → 没流失」，
上线会退化成「只给已经用券的人发券」。对照实验在 Notebook 第 2 节。

**3. 阈值按承接量切，不按 F1**
| 方案 | 触达比例 | 名单流失率 | 召回 | lift |
|---|---:|---:|---:|---:|
| 按承接量（采用） | 6.7% | 43.1% | 22.0% | 3.28 |
| 按 F1 最优 | 23.6% | 30.9% | 55.5% | 2.31 |

多触达 16.9 个百分点的人，只多召回 33 个点的流失用户，边际效率明显下降；而且运营根本发不完。

## 三、结果（同构数据上的方法验证）

| 指标 | 数值 |
|---|---|
| 模型 AUC | 0.774（业务口径 0.78） |
| KS | 0.413 |
| Top 10% 实际流失率 | 39.7%（大盘 13.4%，lift 3.02） |
| 分档单调性 | 是（十分位从 39.7% 单调降到 0.9%） |
| 成本 | 名单触达 28.1 万/月 vs 全量 420 万/月（-93.3%） |

> 这些数字来自**同构数据**，用来验证方法，不冒充业务结果。真实项目里的业务口径是：
> 触达成本 -41%、召回维持在 62%（同等预算下与全量触达对比）。

## 五、环境

只依赖 `pandas` / `numpy` / `matplotlib` / `jupyter`。
**没有用 scikit-learn**：逻辑回归用牛顿法（IRLS）实现，AUC 用秩公式实现，不到 80 行，
好处是每个假设都能讲清楚，坏处是交叉验证要自己写（本项目没做调参，用的是固定 L2=2.0）。

## 六、局限（主动说，别等面试官问）

1. **数据是同构的**：AUC 只证明方法成立，不等于真实业务结果。
2. **随机切分而非时间外验证**：真实项目应按月切（8 月训练、9 月上线、10 月回看），否则会低估线上衰减。
3. **只建了流失概率，没建 UPLIFT**：给谁发券取决于「被券改变行为」的概率，不是「会流失」的概率。
4. **没有分数稳定性监控**：上线后要盯 PSI，特征漂移会让模型悄悄失效。
